# FACTUM — PostgreSQL, API և CMS

Նախագիծը Nuxt 3 / Vue 3 է։ Backend-ը Nitro-ի սերվերային երթուղիներն են։ PostgreSQL-ի հետ կապը Prisma 6-ով է, validation-ը՝ Zod-ով։ Նոր արտաքին CMS չի պահանջվում։ Վիրտուալ գրադարանը չի իրականացվել․ Content-ի տեսակներն ու կապերը հնարավոր է հետագայում ընդլայնել migration-ով։

## Տեղային գործարկում

1. `npm ci`
2. `.env`-ում լրացնել `DATABASE_URL` և `DIRECT_URL`։ Տեղային տարբերակ՝ `postgresql://factum:YOUR_PASSWORD@127.0.0.1:55432/factum?connection_limit=3`։
3. `POSTGRES_PASSWORD`-ը սահմանելուց հետո՝ `docker compose up -d` (կամ օգտագործել գործող PostgreSQL)։
4. `npm run db:migrate`
5. `npm run db:seed`
6. `.env`-ում լրացնել `ADMIN_EMAIL`, առնվազն 12 նիշանոց `ADMIN_PASSWORD`, ցանկության դեպքում՝ `ADMIN_NAME`։ `npm run db:admin`։ Հրամանը չի փոխում գոյություն ունեցող հաշիվը։ Դրանից հետո հեռացնել ադմինի գաղտնաբառը միջավայրից։
7. `npm run dev`։ Մուտք՝ `/login`, կառավարում՝ `/admin`, անձնական էջ՝ `/profile`։

Այս աշխատանքի ընթացքում առանձին տեղային Docker կոնտեյներ է ստեղծվել՝ `factum-cms-postgres`, պորտ՝ 55432, volume՝ `factum-cms-postgres`։ Գործող այլ բազաները չեն փոփոխվել։ `.env`-ում տեղային կապն արդեն ավելացված է։ Կոնտեյների local-only գաղտնաբառը production-ում չօգտագործել։

## Vercel

### Միացված production միջավայր (2026-11-10)

- Նախագիծ՝ `factum2/factum`, կայք՝ https://factum-amber.vercel.app, CMS՝ https://factum-amber.vercel.app/admin։ Node.js՝ 24.x։
- Neon Free PostgreSQL՝ `factum-production`, տարածաշրջան՝ `iad1`։ Երեք migration-ները կիրառված են, սկզբնական 2320 գրառումները ներմուծված են։
- Vercel Blob public պահոց՝ `factum-media`, միացված է Production-ին։
- Production ադմինի տվյալները պահվում են միայն տեղային, Git-ից բացառված `.data/production-admin.txt` ֆայլում։ Գաղտնաբառը Vercel-ի փոփոխականների մեջ չի պահվում։
- Preview-ի համար միացված է առանձին Neon Free `factum-preview` բազան։ `DATABASE_URL`-ը և `DIRECT_URL`-ը սահմանված են միայն Preview միջավայրում. production բազան Preview-ին կցված չէ։
- Հաջորդ թողարկումներն անել CMS ճյուղից կամ այն վերանայելուց և միավորելուց հետո։ Հին `master`-ի deployment-ը կարող է վերադարձնել հին՝ առանց CMS-ի տարբերակը։

- Միացնել PostgreSQL ծառայություն (օրինակ՝ Neon, Supabase կամ Prisma Postgres)։ Runtime-ի `DATABASE_URL`-ը դնել pooled կապով, `DIRECT_URL`-ը՝ direct կապով։ Առանձին բազաներ օգտագործել Preview և Production միջավայրերի համար։
- Սահմանել `NUXT_PUBLIC_SITE_URL=https://your-domain`։ Այն օգտագործվում է նաև հարցումների աղբյուրի ստուգման համար։
- Կիրառել `npm run db:migrate`, ապա առաջին անգամ `npm run db:seed` և անվտանգ միջավայրում `npm run db:admin`։ Migration-ը դիտավորյալ ավտոմատ չի գործարկվում ամեն Preview build-ի ընթացքում՝ production բազան պատահաբար չփոխելու համար։
- `vercel.json`-ի build հրամանը՝ `npm run build:vercel`։ `npm ci`-ի `postinstall`-ը գեներացնում է Prisma client-ը մեկ անգամ, ապա build-ը ստեղծում է Nitro Vercel output-ը։ Հրապարակելուց առաջ առանձին release քայլում կիրառել migration-ները։
- Նկարների վերբեռնման համար նախագծին միացնել Vercel Blob public store և սահմանել `BLOB_READ_WRITE_TOKEN`։ Առանց դրա արդեն տեղադրված նկարների հղումները աշխատում են, իսկ վերբեռնումը հստակ սխալ է վերադարձնում։
- Բազայի backup-ները և վերականգնման քաղաքականությունը կարգավորել ընտրված PostgreSQL ծառայությունում։

Prisma-ի serverless կապերի ուղեցույց՝ https://www.prisma.io/docs/orm/v6/prisma-client/setup-and-configuration/databases-connections

## Կառավարում

- Admin և Editor դերերը կարող են ավելացնել, խմբագրել, հրապարակել և արխիվացնել նյութերը։ Միայն Admin-ը կարող է կառավարել օգտատերերին և հեռացնել գրառումները։ Սովորական հեռացումը պահում է վերականգնելի արխիվացված գրառում։ «Ջնջել անվերադարձ»-ը հասանելի է միայն Admin-ին՝ նյութի խմբագրման էջում։ Անհրաժեշտ է գրել պահպանված ամբողջական անվանումը։ Տեքստը, սևագիրը և հրապարակված տարբերակը ֆիզիկապես ջնջվում են Content աղյուսակից։ Պահվում են միայն ջնջված հասցեի նշումը (DeletedContentKey՝ հետագա seed-ից պաշտպանելու համար) և գործողության audit գրառումը։ Մեդիայի ֆայլերը և առանձին կապված նյութերը ինքնաշխատ չեն ջնջվում։ Բազայի արտաքին backup-ների պահպանումը կարգավորվում է ծառայության քաղաքականությամբ։
- Սևագիրը պահվում է `data`-ում, հանրային տարբերակը՝ `publishedData`-ում։ Հրապարակված նյութի սևագիր խմբագրումը չի փոխում կայքը մինչև «Հրապարակել»-ը։ «Արխիվացնել»-ը հեռացնում է հանրային տարբերակը։
- Նյութի ID-ն և տեսակը ստեղծելուց հետո անփոփոխ են՝ հին հղումները պաշտպանելու համար։ `version`-ը կանխում է խմբագիրների միաժամանակյա փոփոխությունների կորուստը։
- Հարցերի, կենսագրությունների, բաժինների և հուշարձանների ներդրված դաշտերը խմբագրվում են հայերեն ձևերով։ Հայտնի մարդու կենսագրություն կամ դիմանկար փոփոխելիս անհրաժեշտ է ստուգել նաև նրա հուշարձանները և աղբյուրները՝ ըստ AGENTS.md-ի։
- Խաղերի համար ընտրել խաղը, բարդությունը, պատասխանները և ճիշտ պատասխանը (ինդեքսը սկսվում է 0-ից)։ Genius-ի ճիշտ պատասխանը checkbox է։ Միլիոնատերի համար ընտրել բարդությունը և 1–15-րդ հարցերից մեկի առանձին բանկը։ Բանկում հնարավոր է ավելացնել բազմաթիվ հարցեր՝ էջավորված ցանկով։ Յուրաքանչյուր բանկում պետք է առնվազն 2 հրապարակված հարց՝ մեկ հիմնական և մեկ այլ փոխարինող։ Խաղը յուրաքանչյուր հարցահամարի համար պատահական ընտրություն է անում միայն իր բանկից։ Գործող հարցերի համարները պահպանված են։ Genius/Logic-ի համար՝ առնվազն 10։
- «Էջեր» բաժնում `about` և `support` բանալիները կառավարում են համապատասխան էջերը։ Այլ բանալիներով էջերը հասանելի են `/content/KEY` հասցեով։
- «Կայքի տեղեկություններ» բաժնի `footer` բանալին կառավարում է կայքի ստորագրության տեքստը։
- «Մեդիա»-ում կարելի է ավելացնել արդեն օպտիմիզացված տեղային կամ HTTPS հղումներ, հեղինակ և արտոնագիր։ Ֆայլերի վերբեռնումը վերածում է նկարը առավելագույնը 1600×1600 WebP-ի։ Մուտքային սահմանը 800 ԿԲ է։ Նկարի հղումը պատճենել նյութի համապատասխան դաշտում։
- Հեղինակները և կատեգորիաները առանձին բովանդակային գրառումներ են՝ database կապերի աջակցությամբ։ API-ում `authorId` և `categoryId`-ը Content-ի ID-ներն են։
- Կառուցվածքային գիտական գործիքների ծրագրային տրամաբանությունը (օրինակ՝ ատոմի 3D մոդել) մնում է կոդում։ CMS-ը կառավարում է բովանդակային գրառումները, ոչ ծրագրային ալգորիթմները։

## Տվյալների պահպանում և արագություն

Seed-ը պահպանում է սկզբնական ID-ները, աշխատանքների ինդեքսներն ու բոլոր սկզբնական ֆայլերը։ Կրկնակի գործարկումը չի վերագրում CMS-ի փոփոխությունները կամ արխիվացված նյութերը։ Չի ներմուծում գրադարան։ Առանց DATABASE_URL-ի նախկին ֆայլային բովանդակությունը շարունակում է աշխատել։ Կարգավորված բազայի խափանման դեպքում կայքը չի վերականգնում հին՝ հնարավոր է արդեն հեռացված նյութերը։

Բազայի ռեժիմում փոփոխվող էջերը չեն prerender արվում հին տվյալներով։ Public API-ն CDN-ում պահվում է 30 վայրկյան, անձնական և Admin API-ները՝ `private, no-store`։ Ցանկերը էջավորված են՝ հանրային API-ում առավելագույնը 100, Admin-ում 25 գրառում։ Որոնումն ունի PostgreSQL GIN ինդեքս։ Նոր մեդիան lazy/preload=none է։ Գործող մեծ client catalog-ների հին ներմուծումները դեռ որոշ էջերում պահպանված են՝ նախնական ֆունկցիոնալության համատեղելիության համար։

## Authentication

Գաղտնաբառերը scrypt N=131072/r=8/p=1 են՝ պատահական salt-ով։ 256-bit սեսիայի token-ը միայն HttpOnly/SameSite cookie-ում է, բազայում՝ SHA-256 hash-ը։ Production cookie-ն Secure է։ Սեսիան տևում է 14 օր։ Դերի և արգելափակման ստուգումը կատարվում է յուրաքանչյուր պաշտպանված հարցման ժամանակ։ Գաղտնաբառը փոխելը կամ հաշվի դերը փոխելը անվավեր է դարձնում սեսիաները։ Հաշվի ստեղծման հարցումը չի կարող ընտրել Admin դեր։

Գրանցումն ու մուտքը ունեն PostgreSQL-ում պահվող 15 րոպեանոց սահմանափակումներ ըստ IP-ի և էլ․ հասցեի։ Փոփոխող account/admin/auth հարցումները ստուգում են Origin-ը։ Auth token-ները localStorage-ում չեն պահվում։ Էլ․ հասցեի հաստատում, մոռացված գաղտնաբառի mail flow և MFA այս տարբերակում չկան։

«Իմ FACTUM»-ի պահպանված նյութերը `Bookmark`-ում են, ընթերցման և խաղերի առաջընթացը՝ `Progress`-ում։ Առաջին մուտքի ժամանակ սարքի նախկին տվյալները ներմուծվում են մեկ անգամ։ LocalStorage-ը մնում է որպես հյուրի և սարքի քեշ։ Համաժամացման ձախողումը ցուցադրվում է անձնական էջում։ Խաղերի արդյունքներն ինքնահաղորդվող են և մրցակցային վարկանիշի ապացույց չեն։

Պարբերաբար ջնջել ժամկետանց Session/RateLimit գրառումները՝ `npm run db:cleanup` հրամանով՝ վստահելի scheduled job-ից։

## Ստուգումներ

`npm run typecheck`, `npm run test:cms`, `npm run test:people`, `npm run test:monuments`, `npm run build`, `npm run build:vercel`։

Իրական HTTP և PostgreSQL ստուգում՝ գործարկել Nuxt-ը 3011 պորտում, ապա `npm run test:cms:integration`։ Այն ստեղծում և վերջում ջնջում է միայն իր ժամանակավոր հաշիվներն ու փորձնական հոդվածը։ Ստուգում է դերերը, CSRF-ը, հաշիվների մեկուսացումը, սևագիր/հրապարակումը, կոնֆլիկտները, արխիվացումը, հանրային էջերը և ելքը։

Կախվածությունների վերջին audit-ում high/critical խոցելիություններ չեն մնացել։ Կան 14 low/moderate գրառումներ՝ հիմնականում գործող Nuxt/build գործիքների շղթայում․ դրանց ամբողջական վերացումը պահանջում է առանձին Nuxt/tooling թարմացում։ CMS-ի նոր տարբերակը ստուգված է նաև Chrome-ում՝ սևագիր ստեղծելուց մինչև նախադիտում, հրապարակում և անձնական էջում պահպանված նյութը նոր բեռնումից հետո տեսնելը։ Պահպանումը առանձին հաստատվել է PostgreSQL-ում։

## Պարզեցված կառավարման վահանակ և պարտադիր մուտք

CMS-ի գլխավոր էջը ցույց է տալիս իրական հաշվիչներ և վերջին փոփոխությունները։ Նոր նյութի հիմնական ընթացքն է՝ ընտրել բաժինը, լրացնել հայերեն դաշտերը, նախադիտել, ապա հրապարակել։ Բաժիններն ու մարդիկ ընտրվում են որոնվող ցանկերից, հասցեի նշումը ստեղծվում է ինքնաշխատ, իսկ ճիշտ պատասխանը նշվում է պատասխանների կողքին։ «Ինչպե՞ս օգտվել» բաժնում կա ներսում հասանելի ուղեցույց։

Արխիվացված նյութերը հասանելի են կարգավիճակի ֆիլտրով։ Նյութից չպահպանված փոփոխություններով հեռանալիս ցուցադրվում է զգուշացում։ Նկարի ընտրության պատուհանը թույլ է տալիս որոնել պահոցում, վերբեռնել կամ օգտագործել հղում։ Ֆայլերի վերբեռնումը շարունակում է պահանջել կարգավորված Blob ծառայություն։

**Նոր պահանջը գերակայում է վերևում նշված նախկին հանրային ռեժիմին։** Բովանդակության էջերն այժմ բացվում են միայն գրանցումից և մուտքից հետո։ Առանց վավեր սեսիայի էջը տեղափոխում է `/login`, իսկ բովանդակության API-ն վերադարձնում է 401։ Գրանցման և մուտքի API-ները բաց են, իսկ footer-ի տեքստը կարող է օգտագործվել մուտքի էջում։ Admin-ը հասանելի է միայն Admin և Editor դերերին։ Հաջող մուտքից հետո օգտատերը վերադառնում է սկզբում բացած ներքին էջին։

Պաշտպանված HTML/API պատասխաններն ունեն `private, no-store`, ներառյալ CDN-ի հատուկ վերնագրերը։ Բովանդակության էջերը չեն prerender արվում։ Նկարների, տառատեսակների և այլ ընդհանուր ստատիկ ֆայլերի քեշավորումը պահպանված է։ Եթե նախկին տարբերակն արդեն հրապարակվել է Vercel-ում, release-ի ընթացքում պետք է մաքրել նախկին հանրային էջերի CDN քեշը։

«Իմ FACTUM»-ի աղբյուրը PostgreSQL-ի `Bookmark` և `Progress` աղյուսակներն են։ Բրաուզերի քեշը ծառայում է արագ արձագանքի և կապի ժամանակավոր խափանումների համար։ Չուղարկված փոփոխությունները պահվում են տվյալ հաշվին պատկանող հերթում և կրկնվում կապը վերականգնելիս։ Նյութերի ավելացումն ու հեռացումը համաժամացվում են առանձին գործողություններով, որպեսզի մի սարքի չուղարկված փոփոխությունը չջնջի մյուս սարքում ավելացված այլ նյութերը։ Անձնական էջը ցույց է տալիս բեռնման, պահպանման կամ համաժամացման սխալի վիճակը։

## Deployment-ի նախնական ստուգում

Vercel-ի build-ը ստուգում է `DATABASE_URL` և `DIRECT_URL` փոփոխականները։ Դրանք պետք է մատնանշեն արտաքին PostgreSQL ծառայությունը, ոչ `localhost` կամ `127.0.0.1`։ Բացակայող կամ տեղային հասցեների դեպքում deployment-ը կանգնում է հստակ հաղորդագրությամբ, որպեսզի չփոխարինի գործող կայքը չաշխատող CMS-ով։ Սա միայն կարգավորումների ստուգում է․ բազայի իրական կապը և migration-ները նույնպես պետք է ստուգել release-ից առաջ։

`db:seed`, `db:admin` և `db:cleanup` հրամանները կարող են օգտագործել ինչպես `.env` ֆայլը, այնպես էլ միջավայրում արդեն սահմանված փոփոխականները։ Production-ում նախ կարգավորել կապերը, կիրառել `npm run db:migrate`, ապա ներմուծել նյութերը և ստեղծել ադմինիստրատորին։ Տեղային ադմինի հաշիվը նոր production բազայում ինքնաշխատ չի ստեղծվում։ `.env`-ը, գաղտնաբառերը և տեղային բազայի գաղտնի տվյալները Git չեն ուղարկվում։

## Հանրագիտարանի բաժնի նկարն ու շարժվող նախադիտումը

CMS → «Բաժիններ» → նոր բաժին կամ գործող բաժնի խմբագրում։ Լրացնել անունը, ընտրել նկարը և «Քարտի շարժվող նախադիտում» դաշտում վերբեռնել MP4/WebM՝ մինչև 25 ՄԲ։ Այն ուղղակի վերբեռնվում է արդեն միացված Vercel Blob պահոց և սերվերում FFmpeg-ով փոխարկվում է մինչև 8 վրկ, առավելագույնը 960×540, 24 fps, H.264 MP4՝ առանց ձայնի և faststart-ով։ Մշակված ֆայլն առավելագույնը 3 ՄԲ է։ Սկզբնական պատճենը մշակելուց հետո հեռացվում է, չավարտված վերբեռնումներն ունեն 1 օրվա TTL։ Մշակված ֆայլի չափերը գրանցվում են VideoPreview աղյուսակում։

Պահպանել սևագիր կամ հրապարակել։ Նկարը ծառայում է որպես քարտի նախնական պատկեր, իսկ վիդեոն սկսում է բեռնվել միայն hover/focus կամ հպման նախադիտման ժամանակ։ Նույն մեդիան օգտագործվում է գլխավոր էջում և հանրագիտարանի ցանկում։ «Հեռացնել վիդեոն» թողնում է սովորական նկարով քարտը։ Գործող տեղային նախադիտումները պահպանվում են։ Օտար հղումը չի ընդունվում որպես արդեն օպտիմիզացված վիդեո. նոր ֆայլը պետք է անցնի CMS-ի մշակումով։

Vercel build-ը ներառում է ffmpeg-static-ի տվյալ հարթակին համապատասխան binary-ն։ Անհրաժեշտ է միայն գործող BLOB_READ_WRITE_TOKEN-ը և նոր migration-ը։ Ստուգում՝ npm run test:video։ Մեծ աղբյուրները չեն անցնում Vercel Function-ի request body-ով։ Սերվերային միջավայրում անհրաժեշտ է Node.js runtime և binary-ի գործարկման հնարավորություն։
